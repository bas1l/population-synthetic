# Ollama server-side parallelism — full benchmark report

_Generated by `analyze.py` from `sweep_results.jsonl`. Rows analysed: **87/90**. Models with data: 10/11._

> ✅ **Complete.** Excluded (physically won't load at any `num_parallel`): `qwen2.5:72b-instruct-q4_K_M`.

## Setup

- **Server:** `192.168.0.19`, control API `:11435` (reconfigure/status/models), inference `:11434`.
- **Server env** (from `/status`): `CONTEXT_LENGTH=8192`, `FLASH_ATTENTION=1`, `KV_CACHE_TYPE=q8_0`, `MAX_LOADED_MODELS=1`, `KEEP_ALIVE=-1`; `NUM_PARALLEL` varied per run.
- **Method:** for each model, `NUM_PARALLEL` was stepped via the control API (one container restart per level), and at each level `k=NUM_PARALLEL` concurrent requests were fired for three profiles. Metric = **median of 3 trials** (2 for 70B/72B). Throughput as **req/s** and output **tok/s** (rates, so per-level request counts don't bias it).
- **`NUM_PARALLEL` capped at each model's VRAM-recommended max** (from `/models`) to avoid OOM on load. Models capped at 1 (gemma2:9b, all 70B/72B) have no parallelism to measure.
- **Profiles:** `short` = tiny in / short out (baseline); `long_in` = ~1.5-2.4k in / short out (prefill-heavy); `long_out` = tiny in / long gen (decode-heavy).

## Measured load ceiling vs server recommendation

The server's `/models` value is a VRAM-formula *recommendation*. Probing the real limit (reconfigure at rising `num_parallel`, warm-up call, `num_ctx=8192`, `q8_0` KV) revealed the actual constraint is **system RAM, not VRAM** — the failures read `"model requires more system memory (N GiB)"`, i.e. the box is offloading to RAM and accepts *far* more slots than the VRAM recommendation.

> ⚠️ **The load ceiling is NOT the useful ceiling.** These high `max_ok` values are RAM-backed: once a model spills out of VRAM it offloads to CPU and throughput collapses (the two 70B models load up to np=17 but run at ~0.7 tok/s — CPU-bound and unusable). So do **not** set `workers` near the load ceiling; the fast-path limit is where the model still fits in VRAM, which sits between the server recommendation and this ceiling and was not pinned here (a tok/s-cliff sweep would be needed).

## VRAM/offload cliff — raise np, watch tok/s until it collapses

KV cache scales with `num_parallel`. Past the point where weights+KV exceed VRAM, Ollama offloads layers to CPU and single-stream tok/s collapses. This pins the **fast-path max `num_parallel`** — the highest np that stays fully in VRAM (`/api/ps` `size_vram/size == 1.0`) — which is the useful `workers` ceiling.

> Note: measured KV was ~1 GB/slot for an 8B model = **f16**, i.e. the server's `q8_0` KV-cache setting is **not engaging** for at least some models, so VRAM fills ~2× faster than the q8_0 formula predicts (and the fast-path np is correspondingly lower).

## Conclusions

1. **Server-side batching delivers real throughput — measured 1.6×–3.4× (req/s vs serial), scaling with the number of slots the model's VRAM allows** (`deepseek-r1:14b` at 2 slots → 1.60×; `gemma4:e4b` at 12 slots → 3.35×). This corrects an earlier single-shot probe that showed only ~1.2× — that ran while the server was still at `NUM_PARALLEL=1` and used a noisy agg-tok/s metric; this median-of-3 req/s sweep supersedes it (and `RESULTS.md`).
2. **Throughput did NOT plateau within VRAM limits.** The `knee` (95%-of-peak) sits at the VRAM-max for every model, i.e. throughput was still climbing when it ran out of slots. So the server's VRAM-recommended `num_parallel` is worth using — more slots kept helping.
3. **But scaling is sublinear — per-slot efficiency falls as slots rise** (~80% at 2 slots down to ~28% at 12). Each added slot helps less. If per-request latency matters, a lower `num_parallel` (~4) already captures ~2–2.5× for the 8–14B models at much better per-slot efficiency; the full ceiling squeezes out the rest at diminishing return.
4. **At equal concurrency, larger models batch more efficiently** (weights amortise better across a batched pass — the memory-bandwidth argument), but smaller models fit more slots, so they reach a higher *total* speedup. Net: pick `workers` from the VRAM ceiling, not model size.
5. **Profile (input/output length) barely changes the speedup** — `short`, `long_in` (prefill-heavy) and `long_out` (decode-heavy) land within ~0.2× of each other per model. Identity generation's short-to-moderate outputs will see gains in line with the table.
6. **Client action — set `workers` to the server-recommended `num_parallel`, exactly.** The cliff sweep shows that recommendation IS the VRAM boundary: throughput climbs to `rec`, and exceeding it by a single slot collapses tok/s 2–3× (KV spills to CPU). Do NOT chase the RAM-backed load ceiling. The two halves must match — client `workers` = server `num_parallel` — or a batch of 1 wastes the slots.
7. **Highest-value server fix: make `q8_0` KV-cache quantisation actually engage.** Measured KV is ~1 GB/slot (f16) despite `KV_CACHE_TYPE=q8_0` — it is silently falling back. Real q8_0 would ~halve KV and roughly **double** the fast-path slot count per model (more batching for free). Confirm per model that VRAM per slot drops.
8. **The 70B/72B tier is unusable on this ~12 GB GPU** — weights alone exceed VRAM, so they run fully offloaded at ~0.8 tok/s (72B won't load at all). Restrict sweeps to ≤14B models.
9. **Metric caveat:** use req/s (fixed request count) or wall-clock, not raw agg tok/s — output-length variance across runs distorts tok/s ratios.

## Limitations

1. **`gemma2:9b` and the 70B/72B models were swept only at np=1** (their server VRAM rec). The load probe shows they *accept* more slots (gemma2:9b→22, 70B→17) but only via RAM offload, so their parallel throughput was not measured and is expected to be offload-bound — which is likely why the server recommended 1 for them. gemma2:9b uses head_dim=256 (large KV), so few slots fit real VRAM.
2. **The cliff sweep uses single-stream tok/s + `/api/ps` offload fraction** to locate the VRAM boundary (see the cliff section). It does not re-measure *aggregate batched* throughput at each np above the recommendation; the fast-path max np is the offload boundary, and the batched speedup up to the recommendation is the per-model throughput table.
3. **Shared GPU / single box.** Trials were median-aggregated (3, or 2 for 70B) to damp noise, but the server may have served other traffic; per-trial spread is recorded in `sweep_results.jsonl` for audit.
4. **`qwen3:14b`'s first load-probe timed out at 300s** (transient); it was re-probed with a 600s timeout and loads to >=64 like the other 14B models.
